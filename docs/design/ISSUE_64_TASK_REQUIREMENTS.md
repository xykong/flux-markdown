# 可直接执行的任务要求：Issue #64 完整数学渲染

请基于 [FluxMarkdown issue #64](https://github.com/xykong/flux-markdown/issues/64) 的原始附件及后续 MathJax 示例页建议，设计并实施完整数学渲染能力。按仓库 OpenSpec 流程先提交可审阅方案；评审通过后再实现。不要把“页面能打开”“生成了 SVG”或测试无异常等同于数学显示正确。

## 一、分析范围与交付目标

1. 固定 issue、全部评论、原始 zip 和建议页面源码版本，记录来源、SHA-256、环境与复现步骤。逐章分析整份附件，列出标准语法、现有扩展、待支持方言及故意无效样例。
2. 本次实现覆盖附件全部数学项及相关编号/标签/引用/MathML 能力：`$...$`、`$$...$$`、`\(...\)`、`\[...\]`、`math` 围栏；aligned、分式、上下限、矩阵、分段函数、中文 text；`\tag`/`\label`/`\eqref`；原文 MathML。
3. 明确“完美”的可验收定义：原文 11 个有效 TeX 项和 1 个有效 MathML 项全部正确；1 个故意无效命令准确反馈且不破坏后文。转义美元、货币、代码中的公式标记和普通 Markdown 不被误解析。其他 Markdown 方言先完整登记，按独立范围安排，不能混入数学完成率。

## 二、方案必须回答的问题

4. 比较 KaTeX 扩展、整文档 MathJax、双引擎方案，以实际语料、文档级状态、原生离线兼容、性能、导出和可访问性给出选择。不能仅因网页演示可用就复制它的旧版引擎/CDN/全文预处理流程。
5. 首选验证固定版本 MathJax 4 的模块化、文档级方案；字体和组件离线打包。保留 Typst/Mermaid 的既有依赖边界。选择 SVG 或 CHTML 时提供实测及原生宿主证据，不由包的功能介绍代替验证。
6. 在 Markdown token 层识别数学，保留源码与位置，保护代码、HTML 属性、YAML、URL、转义及未闭合输入。覆盖列表、引用、脚注、表格、标题中的公式。禁止以全局正则替换绕过 Markdown 语法优先级。
7. 定义文档级编号与引用：AMS 编号及星号环境、`\tag*`、`\notag`/`\nonumber`、`\ref`/`\eqref`、前向/后向引用、重复/缺失/无编号标签、Unicode 标签、目标失败和锚点冲突。引用必须有正确可见文字、唯一有效目标、鼠标和键盘导航；缺失引用不能只显示可点击的 `(???)`。
8. 明确宏/标签/计数器/字体缓存的生命周期；重渲染、文件切换、旧异步任务返回、设置开关、源码模式、关闭重开后状态正确。避免逐公式 fallback 造成宏和编号分裂。
9. 通过统一输出清理和允许包策略保留合法 MathML/SVG/辅助语义、局部 glyph 和内部链接。处理引擎默认 Worker、字体分片及动态资源，禁止不受控远程加载或任意 TeX 扩展；资源不足/超限时有界失败并保留正文。
10. 接入现有 `ErrorIncident`/`ErrorFeedback`，提供实际可执行的恢复动作及上下文反馈；支持全部现有界面语言。不能上报公式正文、私有路径或原始日志。
11. 更新数学开关的兼容映射、RTL、缩放/字号、搜索/目录/源码复制及导出等待。HTML 离线独立打开仍能显示和跳转；PDF/打印的公式、编号、分页完整，并准确说明和验证链接能力。错误/未完成的公式不能被当成完整成功导出。

## 三、专家级验收要求

12. 在实现前建立人工审定的语料清单和期望：公式结构、符号、矩阵/分段行列、编号值、引用关系、错误和非数学保护样例。禁止由被测实现生成自己的期望结果。
13. 独立参考至少包括：固定版本 LuaLaTeX + amsmath 的两遍编译及 `.aux`/日志、MathML 结构核对、KaTeX 共通子集差分。MathJax 自身的 Node/浏览器双跑只验证接入，不代替独立裁判。不同字体引擎不要求逐像素一致。
14. 分层执行 tokenizer/真实引擎/生产 sanitizer/实际 WKWebView/真实 App、QuickLook、Finder/HTML 与 PDF 导出验证。覆盖明暗主题、窄中宽窗口、200% 缩放、中文和 RTL、当前系统；以语义、几何、截图人工审查及真实键盘/VoiceOver 共同验收。
15. 加入状态变形、性质测试和故障注入：重命名 label、移动公式、重复渲染、A→B→A、宏跨文件隔离、资产缺失、删除引用目标、错编号、丢 SVG defs、漏 await、过期任务等。保存随机 seed 和反例，证明测试能抓住这些真实错误。
16. 先建立固定硬件和语料的冷暖基线，再冻结完成时间、p50/p95、内存、包体及主线程预算。无公式文档不加载数学模块；记录 100/1000 公式压力语料。预算以测量为依据，不能临近交付为通过而放宽。

## 四、交付与完成定义

交付支持矩阵、架构选择记录、OpenSpec proposal/design/spec/tasks、可追溯原始 fixtures、独立预期/参照、实现与回归测试、可重复验证脚本、视觉/导出/交互证据、性能报告及回退策略。遵循 TDD 和每项完成后自动 Conventional Commit。

完成报告必须区分：已实测、源码推断、待验证和本次范围外；明确测试环境及剩余限制。只有全部有效数学项、标签引用、离线宿主、错误恢复和导出达到冻结的验收标准，才能宣告本任务完成。发布、回复 issue 和新增其他方言支持按各自授权与流程执行。
