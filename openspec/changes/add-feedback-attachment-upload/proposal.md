# Change: 真正上传反馈附件并自动带入 GitHub

## Why
用户要求默认附带文件，但当前客户端仅创建本地 ZIP 后打开 GitHub，文件根本未上传。仅预填 issues/new URL 不能带上传二进制附件。当前 backend 只提供计数/运营接口，没有文档附件接口。继续要求用户拖放不能满足此次验收。

## What Changes
- 用户点击“上传附件并继续 GitHub”后才真正上传已选择的 ZIP；取消勾选时仍可不带文件直接反馈。
- 在自有基础设施增加独立的反馈附件服务，不把文档写入遥测数据库，也不受遥测开关支配。
- 上传服务持久化成功并返回校验信息，客户端确认附件可下载后，自动将下载链接写入 GitHub Issue 正文。
- GitHub 页面最终确认发布仍由用户完成。正文附件是自有服务的下载链接，不冒充 GitHub 原生附件对象。
- 上传失败、响应不明、下载验证失败时保留编辑内容和本地文件，提供重试；用户未明确取消附件时不打开缺附件的表单。
- 明示文件先上传到 FluxMarkdown 附件服务，公开 Issue 会公开下载链接；不在 App 内置维护者 GitHub Token、不读取浏览器登录信息。

## Impact
- 客户端：上传状态、取消/重试、幂等、下载校验、固定可信链接的预填与 URL 截断优先级、本地安装验收。
- backend：新增独立启动模式、私有存储及索引、HTTPS 上传/下载、配额与清理；独立 service/user/data directory，与遥测协议隔离。
- 运维：需要在现有基础设施部署新的附件入口，增加存储与备份，不只是更新本地 App。部署必须是明确批准的任务。
- 现有发布制品、版本 tag、Sparkle feed、Homebrew 不改动；此变更不声明 #73 数学根因已修复。

## Approval Requested
同意采用“自有附件服务存放 ZIP，并在 GitHub 正文自动填入下载链接”的实现，以及开发验证后在现有基础设施部署该独立附件服务。若要求文件必须存于 GitHub 而非自有服务，则需要另选包含 GitHub 用户授权的接入方案，不能伪装成预填 URL 可以自动完成。
